Reading a test

How it tests

Automatic
The Mac measures it: kernel facts, devices that appear, data that moves.
Hands-on
You do something: plug in, press, close the lid. The Mac still measures what it can.
Challenge
You answer something only a working part could show you: a code on the screen, a word from the speakers.
Observed
Your plain answer, kept for what no machine can see, like whether the camera picture moves.

How sure it is

  • {{METER high}}A pass needs the part to work end to end. A false pass would take a rare fault.
  • {{METER medium}}The test is sound but leaves a known gap, named on its page.
  • {{METER none}}A live stick can't decide it, like installing to disk. It's left to Omarchy itself.

A test never passes on doubt. When it can't tell, the result is "not tested", with the reason.

boot.watch: the network tests' server

boot.watch is OmaBoot?'s own small server. The Wi-Fi and Ethernet tests move their test data through it and check every byte, both ways, so a sign-in page, a proxy's error page or a broken adapter can't pass for a working network.

The protocol (v1)

Small and public, so a client in any language can use it. Everything is under https://boot.watch/v1/.

RequestAnswerLimits
GET /v1/echo?n=<32 hex>The nonce, as text/plain, exactly as sent (lowercase hex).600 a minute per address
GET /v1/stream?seed=<32 hex>&n=<bytes>The first n bytes of the seed's stream, application/octet-stream, with Content-Length.1 to 1,048,576 bytes; 64 MiB an hour per address
POST /v1/sink?seed=<32 hex> + body{"n": <bytes read>, "match": <leading bytes equal to the seed's stream>}Content-Length required, up to 262,144; 16 MiB an hour per address
GET /v1/healthTotals since start, bytes today and the server's version, as JSON.
  • Every answer carries Cache-Control: no-store, no-transform, so nothing between the Mac and the server can serve a stored copy.
  • Stream and sink bytes also count against 4 GiB a day (UTC) for everyone. Over a limit the answer is 429 with Retry-After.
  • An IPv6 address counts by its /64. Malformed requests get 400, 405, 411 or 413 with a one-line reason.

The stream

AES-128 in counter mode, with the seed as the key and a zero starting counter, over zeros: the keystream itself. Any computer can make the same bytes, so both ends can check them without sending a copy:

head -c 32 /dev/zero | openssl enc -aes-128-ctr -K 000102030405060708090a0b0c0d0e0f -iv 00000000000000000000000000000000 | od -An -tx1 | tr -d ' \n'

A seed means nothing outside its request: the Mac picks a fresh random one each time.

How a network test uses it

Over one connection bound to the adapter under test (SO_BINDTODEVICE), 15 seconds at most:

  1. Sign-in check. An echo over plain HTTP first. A sign-in page can't show inside verified HTTPS, only over plain HTTP: a redirect elsewhere, a 511 or any other page means the network wants a sign-in. A redirect to the same address over HTTPS is only HTTPS being enforced, and is ignored.
  2. Round trip. Six echoes over HTTPS; the last five give the round-trip time. A certificate for another name or from an unknown authority means someone else answered (a sign-in page or a proxy); one outside its dates means the Mac's clock is wrong.
  3. Download. Stream parts of 64 KB and 256 KB, every byte compared.
  4. Upload. 64 KB to the sink; the answer must say all of it matched.
  5. Speed. A 1 MB stream part, cut at 2 seconds, only to measure speed.

The adapter's own byte counters must have grown by at least what moved, so the data really went through it. Data verified both ways passes. A failure counts against the adapter only when boot.watch was there to answer; when the server is down, the test says so instead.

What it keeps

Nothing that identifies you or your Mac. No request log and no addresses on disk; the test data is random and carries nothing. Rate limits are kept in memory per address and forgotten after an hour, and the counters are totals only. It runs on a small server behind Cloudflare that accepts no connections of its own (it dials out), and production runs tagged releases only: /v1/health names the version. More in Privacy.

Watching it

status.boot.watch checks boot.watch every minute the way a Mac does: an echo, 16 KB down and 16 KB up, every byte verified, after a control check so its own network trouble doesn't count against the server. It shows the last 60 days.

Planned: the phone relay planned

  • Pairing: a QR code on the Mac carries a one-time session key after the #, the part of an address a browser never sends. The phone opens boot.watch, both sides connect out to it, and every message is encrypted end to end with that key.
  • The phone's part: read codes on the screen, hear sound-coded words, flash codes at the camera. It decodes on the phone and sends only results.
  • The relay stores nothing, forgets a session when it ends, and limits each address. Its protocol will be documented here too.
  • Every phone step has a manual twin: if the phone goes quiet for 5 seconds, the step switches to the manual way.

T2 Macs: allow the stick

Most Intel Macs from 2018 to 2020, and the iMac Pro, have Apple's T2 chip. It won't start them from a USB stick until you allow it, once, in macOS Recovery. You need an administrator's password.

  1. Start in macOS Recovery. Turn the Mac on and at once hold ⌘ R until the Apple logo appears. If it asks, pick a user and enter their password.

  2. Open Startup Security Utility. In the menu bar: Utilities › Startup Security Utility. When it asks, choose Enter macOS Password and sign in as an administrator.

  3. Turn off Secure Boot for this Mac: under Secure Boot, choose No Security. Medium Security isn't enough: it only starts systems signed by Apple or Microsoft.

  4. Allow the stick: under External Boot, choose Allow booting from external or removable media.

  5. Restart from the Apple menu, then hold Option and pick OmaBoot? Live as on any Mac (Boot it).

To set it back: the same steps, with Full Security and Disallow booting from external or removable media.

FAQ

Does it change my Mac?

No. Before anything else, OmaBoot? Live sets every internal disk read-only, so nothing can write to it. It installs nothing and doesn't write to the firmware, its settings or the startup disk choice.

The only things it writes to are the stick it runs from, when you save a report there, and a stick or card you plug in for a port test. That test writes one temporary file to it and deletes it again.

Which Macs is it for?

Intel Macs, from 2006 to 2020. Omarchy needs a 64-bit processor, so the first Intel Macs of 2006, with a Core Solo or Core Duo, can't run it.

Some early Intel Macs have a 64-bit processor but 32-bit firmware. The stick carries a 32-bit EFI loader for them, and Omarchy's kernel can start from one, but it hasn't been tried on such a Mac yet.

What about T2 Macs?

The Apple T2 Security Chip is in most Intel Macs from 2018 to 2020 and in the iMac Pro. It runs Secure Boot and the internal SSD. The camera and speakers are connected through it, and on laptops the keyboard and trackpad too.

A T2 Mac won't start from a USB stick until you allow it in macOS Recovery's Startup Security Utility. You can set it back afterwards. T2 Macs, step by step

On T2 Macs, OmaBoot? Live starts the t2linux kernel (linux-t2), the kernel Omarchy installs on them. On other Macs it starts Omarchy's standard kernel.

The T1 chip, in the 2016 and 2017 MacBook Pro with Touch Bar, runs the Touch Bar and Touch ID. It doesn't change how the Mac starts from USB.

What if there's no network?

Choose to test offline. Everything runs the same. At the end, save the report to the stick. A way to send a saved report to {{DIO}} later is coming; until then, keep the stick.

Is it official Omarchy?

It runs real Omarchy: built from Omarchy's own ISO, with the same kernels and packages as an official Omarchy release. How to check

It's made by {{DIO}}, not by the Omarchy team. It runs its tests from the text console, without starting the Omarchy desktop, and it has no installer. To install Omarchy, get the official ISO from {{OMARCHY}}.
